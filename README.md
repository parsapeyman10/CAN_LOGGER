# CAN_LOGGER

## Release channel

Current version: **BETA 1.07**. This is a development build, not an ORG (official) release. Continue in the BETA channel and advance the fractional version for future updates (1.01, 1.02, …); do not promote to ORG or change the major version unless the project owner explicitly instructs it. `VERSION` is the version source for the HTML badge, desktop window title and installer metadata. After editing it, run `python3 tools/build_language.py` to regenerate both HTML and the desktop embed and synchronize the installer version. The Windows beta installer uses its own product ID and installation directory. Portable ZIP and installer names include the beta version to distinguish earlier builds.

## Language and getting started

The desktop app opens in English by default. Use **🌐 فارسی / 🌐 English** at the top to switch languages; your selection is remembered on this device when local storage is available. Persian retains the original interface and diagnostic logic.

1. Choose one or more `.log` or `.blf` files in **Add files**.
2. Select the device model if you know it.
3. Choose **Explore requests**, or add two files and choose **Compare files**. Device reference files are optional.

English covers the main workflow and many diagnostic explanations; unusual or custom reference descriptions may still contain Persian. User-supplied file names, reference titles, diagnostic values and analysis are not changed. A warning is evidence for review, not a confirmed fault. CAN results require informed review.

## Rebuilding the embedded desktop document

`CAN_Exchange_Distribution (1).html` is the original distribution. The scripts and styles under `tools/` add the language controls, task cards and summaries without changing the underlying parser. Run `python3 tools/build_language.py --html-only` to update the standalone `app/index.html` without changing the desktop app. The HTML-only command intentionally leaves the desktop app unchanged.

When desktop integration is requested, `python3 tools/build_language.py` also regenerates the compressed document and SHA-256 digest in `Marja_CAN.py`. `Build_Marja.bat` builds the Windows desktop package and runs its smoke test. It creates a new isolated build directory under `%LOCALAPPDATA%\MarjaCAN\Builds` (or `%TEMP%` if LOCALAPPDATA is unavailable), keeping PyInstaller and uv caches out of the project folder. Before packaging, the BAT prints the source folder and checks its version against the Python source, embedded HTML and VERSION file when present. Build directories are retained for diagnostics and may consume significant disk space; delete old directories only when no build is running. Outputs remain in the project’s `installer` folder. If `app/index.html` is present, the BAT checks its content against the integrity-verified embedded desktop document (allowing Windows CRLF line endings) and stops on an actual mismatch; rebuild the desktop embed first. The BAT needs `Marja_CAN.py`, `live_capture.py` and `installer_bootstrap.py` next to it; it can build without the HTML or tools folder. The summaries use the existing application analysis functions; counts describe the selected run or the comparison's current filters, and are not confirmed faults.

The HTML preview colours checked response fields and known lengths: green for matching checked header and known length, orange for a matching header with shorter data, red for a checked mismatch, and neutral where there is insufficient information. Green does not verify every payload value. The assessment follows the selected reference; where the EP6 FD3F length is longer than 77 bytes, acceptance depends on the specification version and remains neutral. Byte tooltips group documented fields and show recorded values and PDF references for selected built-in BCMi, NBCM and SBCM definitions. Coverage is partial; incomplete groups, unknown fields and variant-dependent settings are identified rather than guessed. A selected reference must match the actual ECU. In exchange reports, ISO-TP frame headers, identifiers, session timing pairs and documented data bytes are annotated only when the recorded frames exactly reconstruct the associated message; unassociated raw CAN frames remain uninterpreted.

## Install on another Windows computer

On the build computer run `Build_Marja.bat` and wait for all six steps to succeed. In `installer/`, transfer **`MarjaCAN_BETA_1.07_Installer.exe`** to the target Windows x64 computer and run it. It includes the complete onedir application, Python runtime and Qt files: the target does not need a separate Python, Qt or Inno Setup installation. The installer validates its payload, installs under the current user's `%LOCALAPPDATA%\Programs\MarjaCAN_BETA`, and attempts Desktop and Start Menu shortcuts. It installs alongside existing versions and does not replace them. It is a simple per-user installer, not registered in Windows Apps & Features; remove its installation folder and shortcuts manually if needed. On machines with Inno Setup 6, the BAT also creates the optional `_Setup.exe` with Windows uninstall support.

Alternatively use the versioned `_Portable_x64.zip`: **extract the entire archive**, then run `MarjaCAN\MarjaCAN.exe` with its `_internal` folder intact. Never copy just the executable from `dist`. The one-file installer is generated by the BAT, not included as a prebuilt artifact in this repository. The Windows GitHub Actions workflow also builds it and publishes a temporary workflow artifact; access and availability depend on GitHub Actions permissions and retention. It is unsigned and Windows security policy or antivirus may block it. The actual installer, clean target systems, and Bluetooth hardware have not been tested on Windows in this environment; compatibility with every Windows machine cannot be guaranteed. `tests/installer-bootstrap.py` checks payload integrity and safe/non-destructive extraction without Windows.

## Live serial and Bluetooth capture (desktop)

The desktop toolbar has **Live capture / ضبط زنده**. Connect a serial adapter, or pair a Bluetooth Classic device exposing an SPP COM/serial port in the operating system. Refresh and select that port, set its **serial** baud rate (not CAN bitrate), choose a new filename, and start/stop. The source must already be configured to stream either classic-CAN SLCAN text frames (`t`/`T`, optional SLCAN timestamp) or BUSMASTER-formatted text rows. This is passive: no initialization, polling, CAN transmit or adapter commands are sent. It does not start a monitor mode on an ELM/OBD adapter, read BLE, attach directly to CANoe, or understand arbitrary diagnostic-app protocols. CANoe BLF can still be imported as a file using Add files. To record such sources, they need a compatible serial output or a dedicated adapter integration.

Capture produces two new files without overwriting: a `.raw` file preserving the serial byte stream, and a BUSMASTER-compatible `.log` containing recognized classic CAN frames. The PC reception clock supplies log timestamps, not device timestamps; SLCAN lacks direction, so it is marked Rx on the assumption of a passive stream. Unknown lines are counted and preserved only in `.raw`; CAN FD, remote frames and arbitrary binary formats are not decoded. The preview is limited to the latest 200 lines and may skip display updates without dropping saved frames. A zero-frame recording means no supported frames were identified, not proof the connection is working. After stopping, choose **Analyze saved log** to open the recording directly. For files larger than 64 MiB, use **Add files** instead. Ensure the adapter is configured safely and at the correct CAN bitrate externally.

Install `pyserial>=3.5,<4` as well as the Qt packages for running from source. `Build_Marja.bat` includes it when building on Windows. `tests/live-capture.py` exercises real pyserial against a Linux pseudo-terminal; it does not replace testing a physical adapter, Bluetooth device or Windows build.

## Standalone Windows capture BAT

Run `Capture_Ports.bat` with `capture_ports.py` and `live_capture.py` in the same folder. Python 3 and `pyserial` must already be installed (`py -3 -m pip install pyserial`). The BAT lists operating-system serial ports, including already-paired Bluetooth Classic SPP ports. Enter one or several port numbers (or `ALL`), enter the serial baud rate, then explicitly confirm. Opening any serial port may assert control lines and interfere with software already using it. Choose only devices you are authorized to monitor. Press Enter to stop; files go into a timestamped `captures/` folder next to the BAT. The folder must be writable and is ignored by Git. On an open or write failure the utility reports the affected port and exits with a failure code.

This is not over-the-air Bluetooth sniffing: it cannot discover or decrypt arbitrary wireless traffic, pair devices, use BLE, connect directly to CANoe, or initialize ELM/OBD devices. The same supported input formats and timestamp/direction limitations described above apply. Serial devices must already be streaming. Windows operation with actual adapters has not yet been verified. `tests/capture-ports.py` exercises discovery/confirmation/capture/stop using a Linux pseudo-terminal.

## Testing

`python tests/desktop-embed.py` verifies the embedded HTML, SHA-256, Windows line endings, real mismatches and cache replacement without Qt. For desktop testing, create a virtual environment and install `PyQt6` and `PyQt6-WebEngine`, plus the platform's Qt/WebEngine system libraries. Run `python Marja_CAN.py --smoke-test` in a graphical environment. The optional browser smoke test uses `playwright-core` and a Chromium executable: `NODE_PATH=<node_modules> CHROMIUM=<chromium-path> node tests/browser-smoke.cjs`. It opens both sample log formats and exercises navigation and language switching. It does not replace the desktop smoke test or validate every diagnostic interpretation.

`tests/friendly-workflows.cjs` exercises failed and successful imports, comparison prerequisites, keyboard use and Persian mode. `tests/capture-workflow.cjs` exercises the task choices, bilingual guidance and chunked import into the analyzer. `tests/english-coverage.cjs` scans all 183 requests in the included BUSMASTER sample under each built-in model mapping (using the sample address pair), compares the two sample files, imports the BCMi PDF, and checks live language switching. The alternate model mappings are presentation tests, not assertions that those models describe the sample vehicle. This is regression coverage, not a guarantee for all possible log contents or custom references.

`tests/usability.cjs` checks empty-state guidance, adding a file, request navigation, Persian guidance and a narrow viewport. `tests/explorer.cjs` checks the task cards, diagnostic and comparison summary counts against the underlying analysis, filters, language changes and navigation. `tests/review-status.cjs` covers status colours, short and unknown lengths, hover and keyboard explanations across report views. `tests/diag-groups.cjs` checks documented multi-byte and multi-bit groups, reference isolation and incomplete data. These tests do not replace hands-on usability testing with intended users or the desktop smoke test.
